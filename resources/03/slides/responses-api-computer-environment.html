Responses API 计算环境

Responses API 的关键变化，是把模型从文本生成器推进到可执行环境的协调者。

正确结论：Responses API 的价值不只是新增 shell tool，而是把 shell、托管容器、文件系统、数据库、网络策略、skills 和 compaction 组合成生产级 Agent 工作流底座。

核心结构

Responses API 的计算机环境

  • 核心判断单靠提示只能访问训练好的智能；计算环境让模型能操作文件、运行命令、调用 API 并生成持久产物。
  • 体系结构Responses API 负责编排，shell 提供执行入口，container 提供状态与资源，skills 提供复用，compaction 支撑长任务。
  • 安全边界受控联网、allowlist、egress proxy 和域名级 secret 注入让能力扩展不等于无限制暴露。

The shell tool

精读拆解 · 01

核心转变

01

Responses API 的变化不是“多了一个 shell”，而是把模型、工具执行、文件系统、数据库、网络策略和压缩机制放入同一个可编排请求生命周期。

02

只靠提示词，模型只能产出文本；给模型一个受控计算环境后，它可以运行命令、处理文件、查询结构化数据并生成可验证产物。

03

真实 Agent 工作流会产生中间文件、长日志、表格、网络请求和多轮工具结果，因此平台必须处理超时、重试、输出截断和上下文污染。

04

核心转变是：模型提出下一步，平台执行工具并返回结果，直到模型不再提出 shell command；执行权在受控环境中闭环。

图中循环对应原文的核心机制：模型提出下一步，平台运行工具，结果再回到模型，直到没有新的 shell command 需要执行。

Orchestrating the agent loop

精读拆解 · 02

总体方案

01

托管容器提供隔离执行环境，包含输入输出文件系统、可选 SQLite 数据库、受控网络访问和技能加载能力。

02

shell tool 覆盖范围比单纯 Python code interpreter 更广：它可以运行系统命令、启动服务、调用 CLI、处理文件并组合多语言工具链。

03

容器上下文让开发者不必把所有资料塞进 prompt；大文件、CSV、报告和中间产物可以留在文件系统中，由模型按需读取。

04

这套方案的价值在可重复和可审计：命令、输出、文件变化和策略约束都处于平台控制下，而不是由模型自由想象执行结果。

结构图解 · 03

Responses API + shell + hosted container：容器上下文让文件、数据库和策略受控网络成为模型的工作台。

图中 runtime container 承载文件系统、SQLite、skills 与网络策略；这比把所有输入塞进 prompt 更适合多步任务，因为模型可以按需打开和查询资源。

Orchestrating the agent loop

精读拆解 · 03

Shell Tool

01

模型使用工具的本质是提出工具调用；模型本身不会执行 shell，真正执行发生在 Responses API 管理的隔离容器中。

02

编排器负责读取模型输出、执行命令、收集 stdout/stderr、处理失败，并把工具响应作为下一轮输入交还模型。

03

因此 shell tool 不等于无约束自治：命令仍要受超时、权限、网络策略、输出长度和安全审计约束。

04

把 shell 看成执行入口有助于设计边界：模型负责计划和解释，平台负责执行和控制，应用负责决定哪些工具与资源可见。

结构图解 · 04

Shell 是执行入口，不是自治本身：受控联网依赖 egress proxy，而不是让容器无限访问外网。

图中的 proxy 层表达了原文的安全边界：联网能力需要 allowlist、域名策略、审计和超时控制，避免 shell tool 把执行环境变成无约束浏览器。

Container context

精读拆解 · 04

Agent Loop

01

Agent loop 的基本形态是：模型提出步骤，平台运行工具，工具结果进入上下文，模型再决定下一步，直到返回最终答案。

02

Responses API 可以开箱编排模型与托管工具，减少开发者手写循环、状态拼接、错误恢复和工具响应格式的负担。

03

循环必须能处理非理想状态：命令失败、输出过长、文件缺失、网络不可达或模型提出多个并发命令。

04

生产价值来自可控循环，而不是无限循环；平台需要有终止条件、失败交还和可观测日志，防止工具调用链失控。

结构图解 · 05

编排器把执行变成循环：Skills 把重复流程打包成可确定加载的运行时能力。

图中 registry、bundle 和 runtime 的关系说明 skills 不是提示词片段的堆叠，而是把指令、脚本和资源按需放入容器，降低重复上下文成本。

Network access

精读拆解 · 05

并发与输出控制

01

模型可以在一步中提出多个 shell 命令，Responses API 可用独立容器会话并发执行，从而减少等待时间。

02

并发不是简单加速：每个命令的输出都可能污染上下文，因此平台需要控制输出长度、保留关键头尾并标明省略部分。

03

有界输出让模型看到足够诊断信息，同时避免日志、安装输出或大表格淹没原始任务目标。

04

这解释了为什么执行环境必须和上下文管理一起设计；否则更强的工具能力会直接转化为更严重的上下文负担。

结构图解 · 06

效率与上下文污染同时处理：技能加载需要 registry、bundle 与 runtime 之间的确定路径。

这张图补充说明 skills 的执行边界：平台先从 registry 解析能力，再把必要脚本和资源带入容器，最后由模型按任务需要调用。

Agent skills

精读拆解 · 06

Compaction

01

长时间任务会持续生成命令、文件、错误、重试和决策记录，最终填满上下文窗口。

02

compaction 用更 token 高效的形式保留关键历史状态，让多步、多工具任务能跨上下文边界继续推进。

03

压缩对象应是任务状态、已完成步骤、失败原因、文件位置和下一步计划，而不是把原始日志完整搬进下一轮。

04

这使 Responses API 的容器不仅是执行空间，也是可持续工作记忆的一部分：文件留在环境里，摘要进入模型上下文。

精读拆解 · 07

文件系统

01

容器文件系统适合存放大输入、中间产物、生成报告和代码文件；模型可以按需打开、转换、查询，而不是一次性阅读所有内容。

02

这种设计降低 prompt 膨胀，也让任务产物可复查：文件路径、内容变化和最终输出都能在容器中留下可追踪痕迹。

03

对表格和结构化数据，直接粘贴整表会浪费窗口；更好的做法是放入 SQLite 或文件系统，再由模型生成查询和摘要。

04

文件系统把“上下文”从单个 token 串扩展为工作区，模型只把当前步骤所需信息拉回上下文。

精读拆解 · 08

Network Access

01

受控网络访问让 Agent 可以请求 API、下载依赖或访问文档，但每一次外联都应经过 egress policy，而不是开放任意互联网。

02

网络策略需要限制域名、协议、超时和凭证暴露；否则 shell tool 会把模型错误扩展成供应链、数据泄露或越权访问风险。

03

联网输出也要进入上下文治理：网页、日志或 API 返回可能很长，也可能包含 prompt injection 或与当前任务无关的内容。

04

因此 Network Access 的重点不是“能联网”，而是把联网作为受审计、可回放、可截断的工具能力接入 Agent loop。

精读拆解 · 09

Skills

01

Skills 将重复流程打包为可加载能力，通常包括说明、脚本、资源和使用约定，让模型在运行时按需获得专门工具。

02

与把所有说明常驻 prompt 相比，skills 更接近按需加载：只有相关任务才引入对应上下文，从而减少基础上下文压力。

03

技能加载必须确定、可追踪、可版本化；否则同一个任务在不同运行中看到不同工具说明，会破坏可重复性。

04

在 Responses API 环境里，skills 与文件系统、shell 和容器策略结合，构成可执行 Agent 平台的一层，而不只是提示词模板。

结论

Responses API 的关键变化，是把模型从文本生成器推进到可执行环境的协调者。

OpenAI 说明 Responses API 的价值在于把 shell tool、托管容器、文件系统、数据库、受控网络、skills 与 compaction 组合成可执行、可复用、可长期运行的 Agent 计算环境。
