SUM全文内容总结

Claude 写下了 Claude Code 自身约 90% 的代码，团队由此放弃用“有没有人读过”来判断质量，转而追问：这次改动可能出什么问题，哪一种检查才接得住。答案是七层检查：自我验证、AI 查 bug、安全评审、CI、按风险分级的人工批准、合并队列与开关、快速回滚。人的时间被重新定义为唯一稀缺资源，度量方式也随之明确——每个 PR 的人工批准次数与等待时长，而回滚率与事故率是护栏，一旦上升就说明时间只是被挪走了。

01

评审从关卡变成拼写检查

旧流程是写完代码、开 PR、等人看。新流程让评审持续发生，大多数改动在被交到人手上之前，已经被 Claude 评审并修过至少一轮。

02

人的时间要两头一起算

评审成本包含“看代码”和“修坏代码”两端。只压缩前者，成本会从另一端冒出来，所以回滚率与事故率被设为护栏而不是附带指标。

03

批准强度由改动决定

分类器读取改动本身来定风险档，再由第二个分类器判断是否需要额外的人。作者信任名单只影响能否走轻量路径，Agent 的批准永远不算人的批准。

04

评审器要有评测集和噪音指标

每次事故都进入长期评测集并每日回放；评论按作者反应分类来度量噪音，还会在已知干净的 PR 上统计“若照做会有害”的比例。

05

收敛比召回更稀缺

反复标记的代码里约 59% 在首轮之前就存在。团队因此设三轮上限、只看新 diff、按 bug 类别标记、不重复已发发现。

06

人守住判断与责任

方向、范围、高风险代码、会被效仿的架构、对证据的阅读，以及为每一个上线改动负责——这些不随自动化转移。

OUT结论输出

Final Takeaways
  • 核心判断评审的目标不是“读了多少代码”，而是“哪种检查能接住这类风险”。一旦这样提问，评审的时机、分层和度量方式都会跟着改变。
  • 机制设计七层检查各管一段：前四层靠自动化把常规错误挡在 PR 之外，后三层靠分级批准、合并队列与回滚承接剩余风险，而不是指望某一层做到万无一失。
  • 协作代价当作者和评审者都是 Agent 时，噪音与轮次会被放大：人可以在几秒内挥走一条挑剔的评论，Agent 却会为它再提交一次。收敛机制正是为此而设。
Source-grounded Close
合入一个改动，就意味着出问题时你来修。这个惯例能成立，是因为改动小、一切可逆、爆炸半径决定门槛、遥测能快速暴露回归。
这不是追责：负责修复意味着你掌握最多上下文，事故复盘看的是系统而不是人。开始做一件事很便宜，所以早早关掉一个 PR 也不算损失。

01当 90% 的代码由 Claude 写，评审该怎么做

Core Idea

Claude 写下了 Claude Code 自身约 90% 的代码，团队因此必须换掉“有没有人读过”这个粗指标，改问一个更锋利的问题：这次改动可能出什么问题，哪一种检查才正好能抓住它？

Principles
  • 代码评审有两个职责：上线前拦住问题，以及在团队里传播对代码库的理解。本文的机制设计针对第一个职责，第二个职责留到后文单独讨论。
  • 旧模型把评审当作流程终点的关卡；新模型让评审持续发生，像写作时的拼写检查。等到人来看的时候，大多数改动已经被评审并修过至少一轮。
Source Basis

Claude writes roughly 90 percent of Claude Code's own code, so the team replaced "did a human read it?" with a sharper question: what could go wrong with this change, and which check is the right one to catch it?

Code review does two jobs: catch issues before they ship, and spread codebase understanding. This article targets the first one, and returns to the second near the end.

02真正稀缺的是人的时间与注意力

Core Idea

人的时间有两端：花在评审上的，和花在修复坏代码造成的破坏上的。只削减前者，只是把成本挪到另一端。

Principles
  • 目标是：Claude Code 各仓库中的大多数 PR，在回滚率与事故率不上升的前提下，最多一个人在环内（可以是作者本人）即可合并。
  • 度量方式很明确：PR 的人工批准次数（中位数与 95 分位）、人工评论数、PR 等待某个人的时长。回滚率与事故率是护栏，而不是装点门面的指标。
Source Basis

Human time has two sides: the time spent reviewing, and the time spent repairing what bad code breaks. Cutting only the first just moves the cost to the other end.

The target: most PRs in the Claude Code repos merge with at most one human in the loop, who can be the author, with no increase in reverts or incidents.

03一次变更要穿过七层检查

Core Idea

一个改动依次穿过：先自我验证，再经过 AI 查 bug 与可阻断的安全评审，然后是能拦合并的 CI，接着按风险分级的人工批准，最后进入合并队列、开关与分阶段发布，整个流程下面由快速回滚托底。

Principles
  • 每一层都能抓住一些问题，也都会漏掉另一些问题。很少有改动能毫发无伤地穿过全部检查，所以回滚必须做得平淡、快速、不惊动人。
  • 设计意图是把人的注意力放到真正的风险上，而不是把它均匀地撒在每一个 diff 的每一行上。
Source Basis

A change flows from verified work, through AI bug review and blocking security review, past blocking CI, into risk-tiered human approval, then a merge queue, flags and staged release, with fast rollback underneath everything.

Every layer catches something and misses something else. Few changes survive all of them untouched, which is why rollback is designed to be boring and fast.

04七层检查：从自我验证到快速回滚

Core Idea

第 1 层，在任何人看之前先自我验证：给 Claude 一些能运行的东西（测试、构建、对照设计稿的截图），要求它展示输出而不是宣称完成；随后由子 Agent 在全新上下文中评审 diff。

Principles
  • 第 2 层，每个 PR 都过 AI 评审：把 diff 放进整个仓库与 PR 声明的意图里读；发现先由其他 Agent 交叉投票，再标注 Important、Nit 或 Pre-existing 并按严重程度排序。
  • 第 3 层，可阻断的安全评审：只要 bug 评审或安全评审还有未关闭的发现，PR 就不能合并；若后续提交修好了问题，这条发现会自动消除。
Source Basis

Layer 1, verification before anyone looks: give Claude something it can run (tests, a build, a screenshot against the design) and ask it to show the output instead of claiming success. A subagent then reviews the diff with fresh context.

Layer 2, AI review on every PR: it reads the diff against the whole repo and the PR's stated intent. Findings are cross-voted by other agents before posting, then tagged Important, Nit or Pre-existing and sorted by severity.

05批准强度由改动决定，而不是由作者决定

Core Idea

低风险（文档、文案、仅内部可见的功能、藏在开关后的增量改动）在自动评审与安全检查全绿后无需人工；中风险一人；高风险两人。

Principles
  • 一个分类器读取改动的具体内容来定档，第二个分类器再判断：即便这一档本不需要，这个特定改动是否仍然需要另一个人。
  • 只有仓库信任名单上的作者才能走更轻的路径。Agent 的批准永远不算人的批准：自动评审可以放行低风险改动，却填不上一个本来要求由人占据的位置。
Source Basis

Low risk (docs, copy, internal-only features, additive changes behind a flag) needs no human once automated review and security checks are green; medium needs one person; high needs two.

A classifier reads the change to set the tier, and a second classifier asks whether this particular change needs another person even when the tier says it does not.

06把事故变成评测集，把噪音变成指标

Core Idea

每一次事故都会变成一条长期保留的评测用例，由熟悉那段代码的工程师确认，评审器每天对整个集合打分。

Principles
  • 噪音用行为来度量：每条评论都按作者的反应归类；评审器还会跑在已知干净的 PR 上，统计它给出过多少次会导致有害改动的建议。
  • 更难的一课是收敛：评审器反复标记的代码里约 59% 在它第一轮之前就已存在，多跑几轮主要是在重复翻出旧 bug。
Source Basis

Every incident becomes a permanent eval case, confirmed by engineers who know that code, and the reviewer is scored against the whole set daily.

Noise is measured behaviourally: every comment is classified by how the author responded, and the reviewer also runs on known-clean PRs to count suggestions that would have caused harm.

07自动化之后，人还负责什么

Core Idea

人继续负责方向与范围，负责账单、自动更新器、CI workflow 这类高风险区域，负责会被他人效仿的架构，负责阅读证据，并为每一个上线的改动担责。

Principles
  • 阅读证据指的是测试输出、实际执行的命令及返回、截图、评审器的发现。如果你说不出这些检查会漏掉什么，那就该要求一次真正的评审，而不是随手点通过。
  • 把资深工程师从深度工作中拽出来抓一个常规错误，代价远高于一次自动评审——这正是层与层之间必须划清的原因。
Source Basis

People keep direction and scope, risky areas such as billing, the auto-updater and CI workflows, architecture that others will copy, the reading of evidence, and accountability for whatever ships.

Reading the evidence means test output, the command that ran and what it returned, a screenshot, the reviewer's findings. If you cannot say what the checks would miss, ask for a real review instead of a quick approval.

08机器读代码之后，人怎么学代码

Core Idea

没有人把整个代码库装进脑子里，团队认为也不需要。需要理解时，就让 Claude 针对那一小块写讲解，或者做一个小产物把它可视化。

Principles
  • 与逐行读琐碎的 diff 相比，为“你即将改动的模块”写一份讲解，能把人的注意力花得值得多。
  • 默认在公开 Slack 频道里工作的文化同样重要：别人做东西的过程你能实时看见，反馈也来自并不拥有这段代码的人。
Source Basis

Nobody carries a complete mental model of the codebase, and the team argues nobody needs to. When understanding is needed, Claude writes an explainer for exactly that slice, or builds a small artifact that visualizes it.

Compared with reading trivial diffs line by line, an explainer for the module you are about to change spends human attention far better.

09责任随代码一起落地，流程才搬得走

Core Idea

合入一个改动，就意味着出问题时你来修。这个惯例能成立，是因为改动小、一切可逆、爆炸半径决定门槛、遥测能快速暴露回归。

Principles
  • 这不是追责：负责修复意味着你掌握最多上下文，事故复盘看的是系统而不是人。开始做一件事很便宜，所以早早关掉一个 PR 也不算损失。
  • 给其他团队的清单分四段：PR 之前（CLAUDE.md、本地 /code-review 与 /security-review、一份 REVIEW.md）、每个 PR（CI、AI 评审器、可阻断的安全评审、轮次上限）、批准（把分级写下来、CODEOWNERS、不接受机器人批准）、合并与之后（队列、开关、评测集）。
Source Basis

Landing a change means owning the fix if it breaks. The norm holds because changes are small, everything is reversible, blast radius sets the bar and telemetry surfaces regressions fast.

It is not blame: owning a fix means you hold the most context, and incident reviews examine the system rather than the person. Starting work is cheap, so closing a PR early is not a loss either.

How the Claude Code team does code review

Claude 写下了 Claude Code 自身约 90% 的代码。这支团队随之重写了评审本身：七层检查、按风险分级的人工批准，以及一个会从事故中持续学习的评审器。

重设问题稀缺资源一次变更的旅程七层检查分级批准评审器进化人的位置共享上下文责任与落地
引言：90% 代码由 Claude 写就 · Introduction
We've said before that Claude writes about 90 percent of Claude Code's own code. So how do we review code at the volume we produce it? Does anyone read code anymore? And if something breaks, who catches it?
我们此前说过，Claude 编写了 Claude Code 自身大约 90% 的代码。那么我们如何评审自己产出的这种量级的代码？现在还有人在读代码吗？如果出了问题，谁来接住？
This post covers the code review flow on the Claude Code team and how it has evolved. From June to September, merged pull requests to Claude Code's codebase more than doubled while the share that had to be reverted fell by more than 40 percent. We didn't remove review. But we did move most of the reading to machines, optimized for human time and attention, and invested heavily in making it fast and easy to undo mistakes.
本文介绍 Claude Code 团队的代码评审流程及其演进。6 月到 9 月，合入 Claude Code 代码库的 PR 数量增长了一倍多，而需要回滚的比例下降了 40% 以上。我们并没有取消评审：我们把大部分“阅读”交给机器，围绕人的时间与注意力做优化，并大量投入让撤销错误变得又快又容易。
重新定义代码评审的用途 · Rethinking the purpose of code review
When agents write code, the number of changes goes up, fast. In Anthropic's monorepo, changes landing per day went from about 2,500 in May to more than 30,000 in September this year. Claude Code lives in its own repository, separate from the monorepo, but it's seeing a lot of pressure too. When you are shipping this fast, manual, line-by-line code review is incredibly difficult if not impossible.
当 Agent 开始写代码，变更数量会迅速上升。在 Anthropic 的 monorepo 中，每天落地的变更从今年 5 月的约 2,500 个增长到 9 月的 30,000 多个。Claude Code 位于独立仓库，与 monorepo 分开，但同样承受着巨大压力：以这样的速度交付，逐行的人工评审极其困难，甚至根本不可能。
Code review does two jobs:
1. Find and fix issues before they ship.
2. Build shared context and codebase understanding across the team.
This article mainly focuses on finding and fixing issues, but we will come back to the second job near the end.
代码评审有两个职责：
1. 在上线前发现并修复问题。
2. 在团队中建立共享上下文与对代码库的共同理解。
本文主要讨论第一件事，第二件事留到接近结尾处再谈。
We think "did a human read the code?" is an imprecise proxy for "what could go wrong with this change, and which check—automated or human—is the right one to catch it?" Asking that question also changed when review happens.
我们认为，“有没有人类读过这段代码”是对另一个问题的粗略替代：这次变更可能出什么问题，哪种检查（自动的还是人工的）才正好能抓住它。换一个问法，也改变了评审发生的时机。
Before, review was a gate at the end of the road: write the code, open a PR, wait for your colleague. Now, review runs continuously, more like spellcheck while you write. Most changes have been reviewed and fixed by Claude at least once before a human is asked to look. This catches most routine mistakes, and saves team attention for higher-level questions and scrutiny.
过去，评审是流程终点的关卡：写代码、开 PR、等同事。现在评审是持续的，更像写作过程中的拼写检查。大多数变更在被交到人手上之前，已经由 Claude 评审并修复过至少一轮。这挡掉了大部分常规错误，把团队的注意力留给更高层的问题与判断。
稀缺资源：人的时间与注意力 · The scarce resource
We want to preserve human time and attention for issues only humans can solve and make sure automated checks catch the rest. At our current rate of change, there is still an incredible amount of work for humans to do, and our team encounters new and novel challenges almost daily.
我们希望把人的时间与注意力留给只有人能解决的问题，其余交给自动检查。以当前的变化速度，人要做的事依然极多，团队几乎每天都会遇到新的、前所未有的挑战。
Human time covers both sides of review's cost: the time people spend reviewing, and the time they spend fixing what bad code breaks. Cutting the first doesn't help if the time just shows up in the second.
“人的时间”覆盖评审成本的两端：一是人们花在评审上的时间，二是他们花在修复坏代码所造成的破坏上的时间。如果省下的第一种时间又以第二种形式冒出来，那并没有真正省下什么。
So the goal is that most pull requests in the Claude Code repos (the CLI, the desktop and web apps, and the mobile apps) merge with at most one human in the loop, who can be the author, with no increase in reverts or incidents. To measure human time, we track human approvals per PR (median and 95th percentile), human comments, and how long a PR waits on a person. Revert and incident rates are the guardrail: if they rise, we haven't saved human time, we've only moved it.
因此目标是：Claude Code 各个仓库（CLI、桌面端与 Web 应用、移动应用）中的大多数 PR，在回滚率与事故率不上升的前提下，最多只需要一个人在环内（这个人可以是作者本人）即可合并。为了度量人的时间，我们跟踪每个 PR 的人工批准次数（中位数与 95 分位）、人工评论数，以及 PR 等待某个人的时长。回滚率与事故率是护栏：一旦上升，就说明我们并没有真的省下人的时间，只是把它挪到了别处。
一次变更的旅程 · The life of a change
A typical change, from an engineer's laptop (or a Claude session in Slack), goes through multiple layers of code review.
一次典型的变更，从工程师的笔记本（或 Slack 里的一个 Claude 会话）出发，要经过多层代码评审。
逐层拆解：七层检查 · Layer by layer
1 · The work is verified before anyone else looks. Most review now happens before a PR exists. We give Claude something it can run—like tests, a build or a screenshot to compare against the design—and ask it to show the output instead of saying it's done. Then a subagent reviews the diff with fresh context. Both habits come from our best-practices guide.
第 1 层：在任何人看之前先自我验证。现在大部分评审发生在 PR 存在之前。我们给 Claude 一些它能运行的东西——测试、构建，或一张可与设计稿比对的截图——并要求它展示输出，而不是口头宣称“做完了”。随后由一个子 Agent 在全新上下文中评审这次 diff。这两个习惯都来自我们的最佳实践指南。
Before opening a PR, many of us also run a few internal skills: one hunts for bugs, one simplifies the diff, and one checks the behavior end to end. UI changes also get checked against our design guidelines. Boris Cherny, who created Claude Code, has called giving Claude a way to verify its work probably the most important thing for getting good results. He estimates it makes the final result two to three times better.
在开 PR 之前，很多人还会跑几个内部 skill：一个专门找 bug，一个负责简化 diff，一个做端到端行为检查。UI 变更还要对照设计规范检查。Claude Code 的创造者 Boris Cherny 曾说，给 Claude 一条能验证自己工作的路径，大概是拿到好结果最关键的事。他估计这能让最终结果好上两到三倍。
Verification looks different for each domain. It might be as simple as running a bash command, or running a test suite, or testing the app in a browser or phone simulator. — Boris Cherny
验证在每个领域长得都不一样。它可能只是跑一条 bash 命令，跑一套测试，或者在浏览器、手机模拟器里把应用试一遍。—— Boris Cherny
When the automated reviewer keeps flagging the same thing, we fix it at the source: in the skill, with a lint rule, or with updates to instructional files such as CLAUDE.md and REVIEW.md.
当自动评审器反复标记同一个问题时，我们会在源头修掉它：改 skill、加一条 lint 规则，或者更新 CLAUDE.md、REVIEW.md 这类指导文件。
• CLAUDE.md tells Claude what the project is: the stack, the conventions, the goals and the non-goals. Every review loads it, so in a large codebase we keep it short and point to other docs from there. The reviewer also flags code that breaks a convention in it, and changes that make a line in it out of date.
• CLAUDE.md 告诉 Claude 这个项目是什么：技术栈、约定、目标与非目标。每次评审都会加载它，所以在大型代码库里我们会保持它简短，并从那里指向其他文档。评审器也会标出违反其中约定的代码，以及让某一行约定过时的改动。
• REVIEW.md, written by code owners, tells the reviewer what matters in their part of the code. We check separately whether the reviewer actually follows it. The good ones are short. They say what failure looks like in that repo (for docs it's "it lies," for config it's "it misroutes"), cap the nits, list paths to skip, and ask for a file and line as evidence instead of a guess from a name.
• REVIEW.md 由代码 owner 撰写，告诉评审器在他们负责的那部分代码里什么才是重要的。我们会单独检查评审器是否真的照做。写得好的都很短：说清这个仓库里“失败”长什么样（文档仓库是“它在说谎”，配置仓库是“它把流量路由错了”），限制吹毛求疵的数量，列出可以跳过的路径，并要求给出文件和行号作为证据，而不是靠名字猜。
2 · AI review on every pull request. Every pull request gets a Claude review before a person looks. It reads the diff against the whole repo and the PR's stated intent, and asks: does the change solve its problem, fit the system, or break something else? On a bug fix, it looks for the root cause.
第 2 层：每个 PR 都有 AI 评审。在任何人看之前，每个 PR 都会先过一遍 Claude 评审。它把 diff 放进整个仓库和 PR 声明的意图里去读，追问：这个改动解决了它该解决的问题吗？契合系统吗？有没有弄坏别的东西？如果是一个 bug 修复，它会去找根因。
The public version, Code Review for Claude Code, is now generally available on Team and Enterprise plans, and /code-review runs a lighter version locally. When we launched the research preview, the share of internal PRs getting substantive review comments went from 16% to 54%. Most PRs over 1,000 lines get findings, and most small ones come back clean. Admins set each repo to Quick, Standard, or Deep. Deep is worth it where one missed bug costs more than the extra review time.
公开发布的 Code Review for Claude Code 已在 Team 与 Enterprise 版全面可用，/code-review 命令则在本地跑一个更轻的版本。研究预览上线时，内部 PR 中获得实质评审意见的比例从 16% 升到 54%。超过 1,000 行的 PR 大多能查出问题，小 PR 大多干净返回。管理员可以为每个仓库选择 Quick、Standard 或 Deep 档；当漏掉一个 bug 的代价高于多花的评审时间时，Deep 就是值得的。
Findings get verified by other agents before humans review them. Several agents look for bugs at the same time. Then a separate group votes on each finding, and it only gets posted if enough of them agree it's real. Findings that are only about style, diagnostics, or cleanup get dropped. We A/B tested those filters on our own PRs before keeping them. What's left shows up as inline comments sorted by severity. Each is tagged Important, Nit, or Pre-existing, so a bug the PR didn't introduce doesn't look like the author's fault.
问题在被人类看到之前，先由其他 Agent 验证。多个 Agent 同时找 bug，再由另一组对每条发现投票，票数足够才发出来。只涉及风格、诊断信息或代码清理的发现会被丢掉——这些过滤规则我们都先在自己的 PR 上做过 A/B 才保留。剩下的以行内评论呈现，按严重程度排序，并标注 Important、Nit 或 Pre-existing，这样 PR 之前就存在的 bug 不会被误当成作者的责任。
Every finding has to be answered. You either fix it or resolve the thread with a reason. Often an agent picks up the fix overnight, so the author comes back to a PR that's already been through another round.
每条发现都必须被回应：要么修掉，要么写明理由后关闭讨论。常常是 Agent 在夜里就把修复做了，作者第二天回来时，PR 已经又过了一轮。
3 · Security review that can block. Security gets its own automated review too. A PR can't merge while any finding from the bug review or the security review is still open. You either fix it or close the thread with a short reason, which is how you clear a false positive. If a later commit fixes the issue, the finding clears on its own.
第 3 层：能拦住合并的安全评审。安全有独立的自动评审。只要 bug 评审或安全评审中还有任何一条未关闭的发现，PR 就不能合并；你要么修复，要么用简短理由关闭讨论——这也是清除误报的方式。如果后续某个提交修好了问题，这条发现会自动消除。
You can set up the same thing with the open-source security review GitHub Action or the /security-review command. Setup is covered in automated security reviews in Claude Code.
你可以用开源的 security review GitHub Action 或 /security-review 命令搭起同样的机制，具体配置见 Claude Code 的自动安全评审文档。
4 · Automated checks that block. The usual: lint, type checks, tests on every platform, and a build. (We wrote about scaling CI for this volume.) A typical CLI pull request may run dozens of checks before anyone looks at it. The PR template asks how the change was tested and how to undo it. Claude can fill that in, but the person who asked for the change signs off on it.
第 4 层：能拦住合并的自动检查。都是常规项：lint、类型检查、各平台上的测试，以及构建。一个典型的 CLI PR，在有人看之前可能已经跑了几十项检查。PR 模板会问这次改动用什么方式验证过、以及怎么撤销。Claude 可以替你填，但提出这个改动的人要对它签字确认。
5 · Human approval, scaled by risk. A docs fix and an auto-updater change carry different risk, so they get different review.
第 5 层：按风险分级的人工批准。改一处文档和改自动更新器，风险完全不同，评审强度也不该一样。
RiskExamplesHuman approvals
LowDocs, copy, internal-only features, additive changes behind a flagNone required once automated review and security checks are green
MediumOrdinary product changes, and changes to sensitive areas such as caching, the auto-updater, or system promptsOne person
HighThe highest-risk code, plus a small set of paths that always need two peopleTwo people
风险示例人工批准
低文档、文案、仅内部可见的功能、藏在开关后面的增量改动自动评审与安全检查全绿后无需人工批准
中常规产品改动，以及缓存、自动更新器、系统提示词等敏感区域的改动一人批准
高风险最高的代码，以及一小批始终需要两人确认的路径两人批准
The change sets the tier, not the author. A classifier reads the change and picks its risk tier. A second classifier asks whether this particular change needs another person even when its tier says it doesn't. Some paths always need a person, anything owners have listed as sensitive and any CI workflow file.
分级由改动本身决定，而不是由作者决定。一个分类器读取改动的具体内容，判定它属于哪个风险档；第二个分类器再问：即便这一档本不需要，这个特定改动是否仍然需要另一个人？有些路径永远需要人：owner 标记为敏感的路径，以及任何 CI workflow 文件。
Only trusted authors get the lighter paths. Only authors on the repo's trusted list get the lighter paths, mostly the team that owns it. Everyone else needs a second person to approve. An agent's approval never counts as a person's, either. Automated review can clear a low-risk change, but it can't fill a slot that calls for a human.
只有受信任的作者才能走轻量路径。只有仓库信任名单上的作者（基本就是负责这个仓库的团队）才能走更轻的批准路径，其他人都需要第二个人批准。Agent 的批准永远不算人的批准：自动评审可以放行一个低风险改动，但填不上一个本来要求由人占据的位置。
Whoever prompted the change is on the hook for it. On an agent-written PR, the person directing the agent counts as one of the required reviewers, the same as if they'd typed the code themselves.
谁发起改动，谁就对它负责。在一个由 Agent 写出的 PR 上，指挥 Agent 的那个人算作必需的评审人之一，责任与亲手敲下这些代码时相同。
An approval covers one specific commit. If new commits land that the system can't vouch for, like an agent's push or a merge someone resolved by hand, the approval has to be given again.
一次批准只覆盖一个特定提交。如果之后落入了系统无法担保的新提交——比如 Agent 推送的提交，或某人手工解决的合并——批准就必须重新给出。
6 · Merge queue, flags and a gradual release. The merge queue re-runs every check against main with the change applied, so two PRs that pass separately can't combine into a broken main. New behavior usually ships behind a flag to Anthropic employees first, and our heavy use often surfaces regressions before users do. Public releases go to the latest channel first. The stable channel trails it.
第 6 层：合并队列、开关与渐进发布。合并队列会把改动应用到 main 上重跑所有检查，避免两个各自通过的 PR 合起来把 main 弄坏。新行为通常先藏在开关后面发给 Anthropic 内部员工，我们内部的密集使用往往比用户更早暴露回归。公开发布先进 latest 渠道，stable 渠道随后跟进。
7 · Fast detection, fast rollback. Some mistakes will still get through, so the last layer is about catching them fast. Flags turn off without a deploy. Claude Code has a weekly on-call rotation, and incident reviews ask which layer should have caught the issue.
第 7 层：快速发现、快速回滚。总有些错误会漏过去，所以最后一层比的是发现速度。开关可以不经部署就关掉；Claude Code 有每周轮值的 on-call，事故复盘会追问：哪一层本该拦住它？
Noticing a bad merge still depends on the author and on-call as well as the revert and incident dashboards. We don't yet have circuit breakers that tighten approval when those numbers move; engineers here want them before more code moves to zero-human merges. One colleague said slowing down does lower your error rate, but mostly because you're doing less of everything. We'd rather get faster at noticing and fixing problems.
目前发现坏合并，仍然依赖作者、on-call 以及回滚与事故看板。我们还没有“数字一变就自动收紧审批”的熔断机制；团队里的工程师希望在更多代码走向零人工合并之前把它补上。一位同事说，放慢确实会降低错误率，但那主要是因为你什么都做得更少了。我们宁愿把发现和修复问题的速度提上去。
让评审器变得更好 · How we make the reviewer better
Any incidents are now an eval. The team collected past PRs that caused incidents, with their fix-forwards and reverts, and had engineers who know that code confirm each bug and where it lived. The reviewer runs against that set daily.
每一次事故都会变成一条评测用例。团队收集过去引发事故的 PR（连同它们的修复前进与回滚），请熟悉那段代码的工程师确认每个 bug 以及它藏在哪里，评审器每天都会跑这套集合。
We measure noise by watching what people do with the comments. It's easy to catch more bugs if you don't mind flagging a lot of non-bugs, so we need a check on that. We sort every comment the reviewer leaves by how the person on the PR responded: they fixed it, said it was wrong, said the behavior was intentional, or decided it didn't matter. We also run the reviewer on PRs we know are clean and count how often it reports something that would have led someone to make a harmful change. Our priority, written down, is catching real bugs first and cutting review rounds second.
我们通过观察人们怎么处理评论来衡量噪音。只要不介意误报，多抓 bug 是容易的，所以必须有制衡。我们把评审器留下的每条评论按 PR 上那个人的反应分类：修了、说它错了、说这个行为是有意为之、或认为无关紧要。我们还会在已知干净的 PR 上跑评审器，统计它报出“若照做会产生有害改动”的频率。我们写下来的优先级是：先抓真 bug，再减少评审轮次。
Noise costs more when the author is an agent. A person can wave off a nit in seconds. An agent fixes it, which means another commit and another round of review.
当作者是 Agent 时，噪音的代价更高。人可以在几秒内把一条吹毛求疵的评论挥走；Agent 会去修它，这就意味着又一个提交、又一轮评审。
Review has to converge. An agent author and an agent reviewer can keep each other busy indefinitely. One CLI PR went through more than fifty rounds of review and fixes overnight before its author stopped it.
评审必须收敛。一个 Agent 作者和一个 Agent 评审器可以让彼此无限忙碌下去。有一个 CLI 的 PR，一夜之间经历了五十多轮评审与修复，直到作者出手叫停。
When we ran git blame on what the reviewer kept flagging, about 59% of it was code that had been there since the reviewer's first pass. The reviewer was rarely finding new bugs, it was finding a few more old ones each round. We made it worse ourselves. We'd gotten used to running several rounds by default, since each pass catches something new. This can be worthwhile on a risky change, but not on every PR.
我们对评审器反复标记的代码跑了 git blame，发现其中约 59% 在评审器第一轮时就已经存在。评审器很少在发现新 bug，它只是在每一轮里再翻出几个旧 bug。这一点我们自己也有责任：因为每一轮总能抓到点什么，我们习惯了默认跑好几轮。对高风险改动这也许值得，但不是每个 PR 都值得。
The team now tracks rounds-to-pass alongside recall, and changed re-review:
• A round cap. After three rounds, the reviewer asks the author to step back and reconsider the approach.
• Diff-only re-review after the first few passes.
• Flag the class of bug, so the author fixes every instance, not one line.
• No repeats of findings already posted.
Review agents also run nightly over existing code, helping us catch old bugs before they show up somewhere else.
现在团队把“通过所需轮次”和召回率放在一起跟踪，并改掉了重评审的方式：
• 轮次上限。三轮之后，评审器会请作者退一步重新考虑方案。
• 只看新 diff。首轮之后的评审只针对新增改动。
• 按 bug 类别标记，让作者一次修掉所有同类实例，而不是一行。
• 不重复。已经发过的发现不再重发。
评审 Agent 还会每晚扫一遍现有代码，帮我们在旧 bug 冒到别处之前抓住它。
人类仍然守着的位置 · Where humans stay in the loop
Pulling a senior engineer out of deep work to catch a routine mistake costs far more than an automated review. People on the team are still responsible for:
• Deciding whether to build it. Direction, taste and scope.
• Reviewing risky code such as billing, the auto-updater and CI workflows.
• Reviewing architecture that sets a pattern others will copy.
• Reading the evidence.
• Owning the outcome.
把一位资深工程师从深度工作中拽出来抓一个常规错误，代价远高于一次自动评审。团队里的人依然要负责：
• 决定这件事该不该做。方向、品味与范围。
• 评审高风险代码，例如账单、自动更新器和 CI workflow。
• 评审架构，尤其是会被他人效仿的模式。
• 阅读证据。
• 为结果负责。
One team that declared its review bottleneck solved still kept human review for changes from outside the team, so someone asks "should we even do this?"
有一个团队宣布自己的评审瓶颈已经解决，但对来自团队外部的改动依然保留人工评审——总得有人来问一句：“这件事我们到底该不该做？”
Reading the evidence means test output, the command that ran and what it returned, a screenshot, the reviewer's findings. If you can't say what the checks would miss, ask for a real review rather than a quick approval.
“阅读证据”指的是测试输出、实际执行的命令及其返回、截图、评审器的发现。如果你说不出这些检查会漏掉什么，那就该要求一次真正的评审，而不是随手点个通过。
Owning the outcome: a person is accountable for every change that ships, whoever typed it.
为结果负责：每一个上线的改动都有人对其负责，不管代码是谁敲的。
团队内共享上下文 · Sharing context across the team
Code review's second job has always been to spread codebase understanding. Reading a teammate's diff is how you learn what changed and how the pieces fit. If machines do most of the reading, how does anyone learn the code?
代码评审的第二个职责一直是传播对代码库的理解。读同事的 diff，是了解改了什么、各部件如何咬合的方式。如果大部分阅读都由机器完成，人还怎么学这套代码？
We don't have a formal process for this. Nobody on the team keeps a complete mental model of Claude Code in their head, and we don't think anyone needs to. When someone wants to understand a part of the codebase, they ask Claude to write an explainer for exactly that slice. It takes minutes and reflects the code as it is today.
我们对此没有正式流程。团队里没有人把 Claude Code 的完整心智模型装在大脑里，我们认为也不需要。当有人想弄懂代码库的某一部分时，就让 Claude 针对那一小块写一份讲解，几分钟就好，而且反映的是今天的代码。
Some of us go a step further and have Claude build a small artifact that visualizes that part of the code and teaches it the way that person likes to learn. If the goal is to spend human attention well, this beats reading trivial diffs line by line. A one-line copy change teaches you almost nothing. An explainer for the module you're about to change teaches you a lot.
有些人更进一步，让 Claude 做一个小产物，把那一部分代码可视化，并按这个人喜欢的学法学给它听。如果目标是让人把注意力花得值，这比逐行读那些琐碎的 diff 好得多：一行文案改动能教给你的几乎为零，而针对你即将改动的模块写一份讲解，能教给你很多。
Our culture of defaulting to working on open Slack channels helps too, since you see what others are building while they build it.
我们默认在公开 Slack 频道里工作的文化也有帮助：别人做东西的过程，你能实时看见。
"你合入，你负责" · You land it, you own it
If you land a small or medium change and something still goes wrong, it's a team norm that you usually fix it. A few things keep this from going badly:
• Changes are small, so they're easy to review, debug and revert.
• Everything is reversible. Flags, reverts and staged releases undo most mistakes in minutes.
• Blast radius sets the bar. Expensive code gets more people and more checks.
• Regressions surface fast through telemetry and internal use.
• It isn't blame. Owning a fix means you have the most context; incident reviews look at the system.
如果你合入了一个小或中等规模的改动，后来出了问题，团队惯例是你自己去修。有几件事让这个惯例不至于变糟：
• 改动都很小，因此容易评审、调试和回滚。
• 一切都是可逆的。开关、回滚和分阶段发布能在几分钟内撤销大部分错误。
• 爆炸半径决定门槛。代价高的代码会获得更多人和更多检查。
• 回归很快浮现，靠遥测和内部使用。
• 这不是追责。负责修复意味着你掌握最多上下文；事故复盘看的是系统。
Ownership is also shared. Much of the team works in open channels where anyone can see what others are building, pick up a thread, or point a Claude at a gap, and feedback comes from people who don't own the code too. That openness is a big part of how quality stays high without a gate on every line.
责任也是共享的。团队大部分工作在公开频道里进行，任何人都能看到别人在做什么、接上一条线索，或把一个 Claude 指到一个缺口上；反馈也来自并不拥有这段代码的人。这种开放，是在不对每一行设关卡的前提下仍能保持高质量的重要原因。
当我们改变方向 · When we change direction
Agents make it cheap to start things, so some work shouldn't land. Usually someone in the channel asks why, points at an earlier decision, or suggests a simpler route, and the author closes or reshapes the PR. Since the code was fast to write, closing the PR doesn't feel like a loss.
Agent 让“开始做点什么”变得很便宜，所以总有些活不该落地。通常是频道里有人问一句为什么、指回之前的某个决定，或提出一条更简单的路径，作者就把 PR 关掉或重塑。既然代码写得快，关掉 PR 也不像是一种损失。
The trick is to raise a different direction in the thread early, not as a blocking comment on a finished PR.
诀窍在于趁早在线程里提出不同方向，而不是等到 PR 做完再丢一个阻断性评论。
如何把这套流程搬到你的团队 · How you can adopt this process
Most of the pieces to do this with your team exist today.
Before the pull request
• Give your agent checks it can run, listed in a short CLAUDE.md, plus hooks that run formatters and linters.
• Run /code-review and /security-review locally, or a fresh-context subagent review.
• Add a REVIEW.md, and move repeated review comments into it.
要在你自己的团队里这么做，大多数零件今天都已经有了。
在 PR 之前
• 给 Agent 一些它能跑的检查，写在简短的 CLAUDE.md 里，再加上运行格式化和 lint 的 hook。
• 在本地跑 /code-review 与 /security-review，或让一个全新上下文的子 Agent 评审。
• 加一份 REVIEW.md，把重复出现的评审意见搬进去。
On every pull request
• Require CI, and add "Testing", "Risk" and "How to revert" to your PR template.
• Add an AI reviewer (Code Review for Claude Code, or the Claude Code GitHub Action) on one repo, tune REVIEW.md for a few weeks, then widen.
• Add automated security review, and require every review thread resolved before merge.
• Match review effort to risk: a quick pass on routine changes, a deep one where a missed bug is expensive (Quick, Standard or Deep in Code Review).
• Cap review rounds; after the first few, re-review only the new diff.
在每个 PR 上
• 强制 CI，并在 PR 模板里加上“如何测试”“风险”“如何回滚”。
• 先在一个仓库接入 AI 评审器（Code Review for Claude Code，或 Claude Code GitHub Action），花几周调整 REVIEW.md，再逐步铺开。
• 加上自动安全评审，并要求合并前所有评审线程都已解决。
• 让评审强度与风险匹配：常规改动快速过一遍，漏一个 bug 代价高的地方就深评（Code Review 里的 Quick、Standard、Deep）。
• 限制评审轮次；首轮之后只重评审新增 diff。
Approval
• Write down risk tiers, set from the change rather than the author; start strict and loosen with evidence.
• Keep the lighter approval paths for authors you trust.
• Use CODEOWNERS and branch protection so auth, billing, CI and release workflows, and installers always need a person.
• Never let a bot's approval replace a required human's; dismiss approvals on new commits.
批准环节
• 把风险分级写下来，按改动而非作者分级；从严开始，有证据再放宽。
• 把更轻的批准路径留给你信任的作者。
• 用 CODEOWNERS 与分支保护，让认证、账单、CI 与发布 workflow、安装器永远需要人。
• 绝不让机器人的批准替代必需的人类批准；出现新提交时作废旧批准。
Merge and after
• Use a merge queue, feature flags, internal use first, staged releases and one-step rollback.
• Turn incidents and reverts into an eval set, and rescore the reviewer whenever its prompts, tools or model change.
• Measure human time, with revert and incident rates as the guardrail.
合并与之后
• 使用合并队列、功能开关、内部先用、分阶段发布与一键回滚。
• 把事故与回滚变成评测集，每当评审器的提示词、工具或模型变化时重新打分。
• 度量人的时间，并以回滚率与事故率作为护栏。
走向何方 · Where this is going
Code Review's announcement said approving a pull request is still a human call; the product posts findings, not approvals. Our own repos go further, letting owners decide which low-risk changes merge on automated checks alone, and that line keeps moving.
Code Review 的发布公告说，批准一个 PR 仍然得由人来做；产品只发布发现，不发布批准。我们自己的仓库走得更远：由 owner 决定哪些低风险改动可以只凭自动检查合并，而这条线一直在移动。
When a review misses something, we ask what the model didn't have in front of it and put the fix into a CLAUDE.md, a skill or a new check. The goal hasn't changed: less human time per change, and no more reverts than before.
当评审漏掉了什么，我们会问：模型当时眼前缺了什么？然后把修复写进 CLAUDE.md、一个 skill，或一条新的检查。目标没有变：每次变更花掉的人的时间更少，回滚不比以前多。
If your team lets agents open pull requests, we'd like to hear which checks you've automated, which still need a person, and what you think we have wrong.
如果你的团队也让 Agent 开 PR，我们很想知道：你把哪些检查自动化了，哪些仍然需要人，以及你觉得我们哪里做错了。
