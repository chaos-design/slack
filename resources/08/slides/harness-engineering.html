Harness Engineering：Agent-first 时代的工程组织方式

OpenAI 团队刻意采用“0 行人工手写代码”的约束：人类负责设定目标、表达验收标准和编码判断力，Codex 负责执行、审查、修复和合并。这个实验显示，Agent-first 工程的稀缺资源是人类注意力，因此系统必须把 UI、日志、指标、文档、架构规则和质量标准变成 Agent 可直接读取和执行的形式。

原文：Harness engineering: leveraging Codex in an agent-first world

核心主张

先理解文章真正要解决的问题

文章的核心不是“让 Agent 多写代码”，而是把软件工程系统改造成 Agent 能理解、验证、修复和持续改进的运行环境。
  • 工程师的主要工作转为设计 harness：工具、脚手架、约束、文档和反馈回路。
  • AGENTS.md 不应成为巨型说明书，而应成为通向仓库内知识系统的目录。
  • 架构约束、结构测试、自定义 lint 和错误信息共同构成可执行的“品味”。

结构速览

文章如何组织论证

01

从空仓库到百万行代码

文章从一个强约束实验开始：从空 Git 仓库出发，五个月内由 Codex 生成约百万行代码、合并约 1,500 个 PR，并支撑真实内部用户。重点不是炫耀代码量，而是观察当“人类不再亲自写代码”时，工程系统需要怎样变化。

02

工程师角色转向 harness 设计

人的工作从实现细节上移到系统设计：拆任务、补工具、写可执行规则、把反馈做成循环。失败被视为系统能力缺口，而不是一次提示词不够用力。

03

让应用对 Agent 可读

随着代码吞吐提升，瓶颈变成人类 QA。OpenAI 的做法是把浏览器、DOM、截图、日志、指标和 tracing 暴露给 Codex，使 Agent 能在隔离 worktree 中启动应用、复现问题并验证修复。

04

仓库知识成为记录系统

文章反对把所有规则塞进一个巨大的 AGENTS.md。更有效的方式是让 AGENTS.md 成为地图，真正的知识沉淀在仓库内的 docs、plans、architecture、quality 和 generated schema 中，并通过 lint/CI 维护新鲜度。

05

架构和品味需要机械化

Agent-first 代码库不能只靠文档保持一致性。OpenAI 把依赖方向、领域分层、日志结构、命名、文件大小和平台可靠性做成可检查规则，并把错误信息写成 Agent 可直接执行的修复说明。

06

吞吐量改变合并策略

当 Agent 的产出速度超过人类注意力，传统“长时间阻塞合并”的策略会变得昂贵。文章强调短 PR、少阻塞门和后续快速修复；这只有在自动化验证和持续清理能力足够强时才成立。
