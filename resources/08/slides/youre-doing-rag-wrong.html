核心主张

先理解文章真正要解决的问题

这篇文章的核心观点是：RAG 的关键改造点不一定在检索算法，而在进入向量库之前的知识单位设计。
  • chunk-as-unit 是检索失败的重要上游假设。
  • 把问题、验证答案和治理字段组成一个可检索、可治理的原子声明。
  • 语义去重与结构化治理让检索表面更清晰，更新也能从单条记录传播。

从 chunk 假设开始的问题

文章指出，RAG 的许多失败并不一定来自检索算法、reranker 或 embedding model，而是来自更上游的默认假设：把一段文本 chunk 当作知识嵌入的基本单位。作者声称，新的预处理方式可以让语料规模减少 40x、每次查询 token 减少 3x，并将向量检索相关性提升 2.3x。

为什么 chunk 不是好的知识单元

chunk 只是结构中性的容器，不知道观点边界、文档版本，也不知道访问权限。按 token 数切分会造成半张表、缺少论证的结论、脱离上下文的声明被检索出来；企业语料中的重复版本还会让 Top-K 返回多个近似段落，混合当前版和废弃版。访问控制、版本状态和权限等级如果只挂在编排器上，就会与内容本身脱节。

更好的单位：Question-Answer Packet

作者提出的替代单位是 Question-Answer Packet：一个问题、一个经过验证的答案，以及以类型化 schema 表示的治理字段。Blockify 将这种结构称为 IdeaBlock，把 clearance level、version state、source 等字段与答案放在同一个对象上。由于用户查询天然是问题，索引中也存储问题对应的答案，匹配就从单纯语义相似变。

反直觉结果：更少数据带来更高准确性

语义蒸馏的反直觉之处在于，缩小语料并不必然损害检索。作者给出的 Blockify 内部基准显示，2,042 个原始 IdeaBlocks 经 3 到 5 轮、80-85% 相似度阈值的迭代去重后，压缩为 1,200 个 canonical IdeaBlocks；词数从 88,877 降至 44,537；蒸馏后的数据集在向量准确性上高出 13.55%。原因是大量近重复段落会在。

从文档到 IdeaBlocks 的七阶段管线

作者把改造点放在进入向量库之前的预处理层。Blockify 的流程包含七步：先定义 Organization、Business Unit、Product、Persona 等索引层级；再接收 DOCX、PDF、PPT、图片、Markdown、HTML 等文档；由 LLM 层把原始 chunk 转为草稿 IdeaBlocks；然后做语义去重、自动打治理标签、交给领域专家验证，最后。

The fix is a preprocessing pipeline that runs before anything touches the vector store. Blockify’s processing runs in seven stage。

应用层会发生什么变化

嵌入的知识单位决定应用层能做什么。查询构造会更简单，因为查询本来就是问题，而索引中存的是问题的答案；治理也会下沉到数据层，因为角色访问、版本状态和权限等级成为每个 block 的类型化字段；更新则可以从单条记录传播，规格变化时更新一个 IdeaBlock，所有查询该 block 的应用下次即可得到修正答案。架构并不改变查询方式，而是改变你能否信任答案。
