Anthropic 工程原则

复杂度必须由评估证明，而不是由架构欲望驱动。

本文是 Anthropic 关于构建高效 AI agent 的工程实践总结：最成功的实现往往不依赖复杂框架，而是使用简单、可组合的模式；应先用最简单的方案，仅在评估证明确有必要时才逐步增加复杂度。

    Parallelization

    01

    Prompt chaining 把一个任务拆解成一连串步骤，每次 LLM 调用都处理前一步的输出。你可以在任意中间步骤上加入程序化检查（见下图中的 "gate"），以确保整个流程仍在正轨上。

    02

    何时使用此 workflow：当任务能够被轻松、干净地拆分为固定子任务时，这种 workflow 最为理想。它的主要目标是通过让每次 LLM 调用都更简单，以延迟换取更高的准确率。

    03

    Prompt chaining 适用的示例：
    • 先生成营销文案，再把它翻译成另一种语言。
    • 先撰写文档大纲，检查大纲是否满足特定标准，然后基于该大纲撰写文档。

    Orchestrator-workers

    01

    Routing 对输入进行分类，并将其导向专门的后续任务。这种 workflow 实现了关注点分离，并能构建更专门的提示词。如果没有这种 workflow，针对某一类输入做优化可能会损害对其他输入的表现。

    02

    何时使用此 workflow：当复杂任务存在适合分开处理的不同类别，且分类可以由 LLM 或更传统的分类模型/算法准确完成时，Routing 表现良好。

    03

    Routing 适用的示例：
    • 把不同类型的客服查询（一般问题、退款请求、技术支持）导向不同的下游流程、提示词和工具。
    • 把简单/常见问题路由到成本更低的模型，把困难/少见问题路由到能力更强的模型，以优化整体表现。

    精读拆解 · 06

    Evaluator-optimizer

    01

    LLM 有时可以同时处理一个任务，并通过程序把它们的输出汇总起来。这种 workflow——parallelization（并行化）——主要表现为两种形式：

    02

    分区（Sectioning）：把一个任务拆成多个相互独立、可并行运行的子任务。投票（Voting）：对同一个任务多次运行，以获得多样化的输出。

    03

    何时使用此 workflow：当拆分出的子任务可以并行执行以提升速度，或者当需要多个视角或多次尝试来获得更高置信度的结果时，parallelization 很有效。对于涉及多重考量的复杂任务，让每一项考量由单独的 LLM 调用来处理通常表现更好，因为这能让模型专注于每个具体方面。

    04

    Workflow: Parallelization 适用的示例：
    • 分区：一个模型处理用户查询，另一个模型筛查不当内容或请求，用于实现更稳健的护栏。
    • 分区：自动化 eval 时，让不同 LLM 调用分别评估同一提示下模型表现的不同方面。
    • 投票：让多个提示审查同一段代码的漏洞，只要发现问题就标记。
    • 投票：多个提示从不同角度判断内容是否不当，并通过不同阈值平衡误报和漏报。

    精读拆解 · 07

    Agents

    01

    在 orchestrator-workers（编排者-工作者）workflow 中，一个中心 LLM 动态地拆解任务，把它们委派给作为 worker 的 LLM，并综合这些 worker 的结果。

    02

    何时使用此 workflow：当复杂任务所需的子任务无法预先预测时，这种 workflow 非常合适（例如在编码中，需要改动的文件数量以及每个文件改动的性质，往往取决于具体任务）。虽然它在结构上与 parallelization 类似，但关键区别在于灵活性——子任务不是预先定义好的，而是由编排者根据具体输入来决定的。

    03

    Orchestrator-workers 适用的示例：
    • 每次都需要对多个文件做复杂修改的编码产品。
    • 需要从多个来源收集并分析信息，以寻找潜在相关内容的搜索任务。

    精读拆解 · 08

    Workflow: Evaluator-optimizer

    01

    在 evaluator-optimizer（评估者-优化者）workflow 中，一个 LLM 调用生成响应，另一个 LLM 调用则在循环中提供评估和反馈。

    02

    何时使用此 workflow：当我们有清晰的评估标准、且迭代式打磨能带来可衡量的价值时，这种 workflow 特别有效。两个适配良好的标志是：第一，当人类把反馈清楚地表述出来时，LLM 的响应能够明显改进；第二，LLM 自身能够提供这样的反馈。这类似于人类作者打磨一篇成稿文档时所经历的反复修改过程。

    03

    Evaluator-optimizer 适用的示例：
    • 文学翻译：译者 LLM 起初可能漏掉细微差别，而评估 LLM 能提供有用批评。
    • 复杂搜索任务：需要多轮搜索和分析来收集完整信息，由评估者判断是否还需要继续搜索。

    精读拆解 · 09

    Agents

    01

    随着 LLM 在一些关键能力上日益成熟——理解复杂输入、进行推理和规划、可靠地使用工具、以及从错误中恢复——agent 正在生产环境中崭露头角。Agent 的工作始于来自人类用户的指令，或与用户的交互式讨论。一旦任务明确，agent 便会独立地规划和执行，必要时会回到人类那里获取更多信息或判断。在执行过程中，agent 在每一步从环境中获得"真实反馈"（ground truth，例如工具调用结果或代码执行结果）至关重要，以此评估自身进展。Agent 随后可以在检查点处、或遇到障碍时暂停以获取人类反馈。任务通常在完成时终止，但加入停止条件（例如最大迭代次数）以保持可控，也很常见。

    02

    Agent 能够处理复杂任务，但它们的实现往往很直接。它们通常只是 LLM 在一个循环中、根据环境反馈来使用工具。因此，清晰而周到地设计工具集及其文档至关重要。我们在附录 2（"Prompt Engineering your Tools"）中详细展开了工具开发的最佳实践。

    03

    何时使用 agent：agent 适用于开放式问题——这类问题难以甚至无法预测所需步骤数量，也无法硬编码出一条固定路径。LLM 可能会运行很多个回合，因此你必须对它的决策有一定程度的信任。Agent 的自主性使它们非常适合在可信环境中规模化地执行任务。

    04

    Agents 适用的示例：
    • 用于解决 SWE-bench 任务的编码 Agent，这类任务需要根据任务描述编辑许多文件。
    • Anthropic 的 computer use 参考实现，其中 Claude 使用计算机完成任务。

    结论

    复杂度必须由评估证明，而不是由架构欲望驱动。

    Anthropic 总结了构建 Agent 的工程原则：从简单 LLM 调用开始，用评估驱动复杂度升级，并在 workflow 与 autonomous agent 之间做清晰取舍。
