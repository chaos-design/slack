精读拆解 · 01

任务前提

01

文章讨论的不是把科学研究完全外包给模型，而是把清晰目标、可量化成功标准和偶发人工监督结合起来，让 agent 在较长时间尺度上推进科学计算代码任务。

02

适用前提是任务边界足够明确：例如重实现 numerical solver、迁移旧 Fortran 科学软件、或用 reference implementation 调试大型代码库。

03

这类任务与开放式科学发现不同。Agent 必须能通过 reference implementation、objective metric 或 existing test suite 判断自己是否在进步。

04

文章的实践场景是典型 academic lab：研究者有高层目标和有限监督时间，Claude Code 负责长时间执行、记录进展、运行测试并在必要时请求人类 steering。

精读拆解 · 02

适合任务

01

适合任务通常具备三个条件：work well-scoped、success criteria clear、human oversight occasional rather than continuous。缺少这些条件时，长时间自治只会放大错误。

02

作者列举的任务包括：reimplementing a numerical solver、converting legacy scientific software in old Fortran dialect to a modern language、debugging against a reference implementation。

03

C 编译器项目可以大量并行拆给约 2,000 sessions；Boltzmann solver 则是 deeply coupled pipeline，微小数值误差会沿着 photons、baryons、neutrinos、dark matter 的耦合方程传导。

04

因此科学计算长任务更依赖单个 agent 顺序推进、必要时 spawning subagents，并用 reference implementation bisect discrepancies，而不是简单扩大并行 agent 数量。

精读拆解 · 03

具体案例

01

具体案例是用 Claude Opus 4.6 实现 differentiable version of a cosmological Boltzmann solver，即 `clax` 项目，用来预测 Cosmic Microwave Background 的统计性质。

02

参考对象是 CLASS 和 CAMB 这类宇宙学基础设施，它们用于基于 Planck、Simons Observatory 等观测数据约束 cosmological models。

03

作者并非该细分领域专家，这一点很关键：实验目标是观察 agent 能否在非核心专业领域中，通过明确目标、参考实现和持续测试推进复杂科学代码。

04

目标不是声称 agent 已替代领域专家，而是验证在有 oracle 和清晰误差指标时，长任务 coding workflow 能否显著压缩 researcher-time。

精读拆解 · 04

科学价值

01

Differentiable solver 的价值在于能把 gradients 传过完整 solver，从而使用 gradient-based inference methods，大幅加速 parameter estimation。

02

JAX 是自然选择，因为它同时提供 automatic differentiation 和 accelerator compatibility，例如 GPU 支持，这些能力对现代数值推断工作流很重要。

03

精度目标设为 main science deliverables 与 CLASS 达到 0.1% agreement，因为 CLASS 与 CAMB 这两个 canonical Boltzmann codes 之间通常也以这个量级作为比较标准。

04

文章同时承认边界：最终 solver reached sub-percent agreement across outputs，但并非 production-grade，也没有在每个 regime 都达到 reference CLASS 的可接受精度。

精读拆解 · 05

执行框架

01

`CLAUDE.md` 是项目说明和执行规则的锚点：它放在 repo root，写明 deliverables、相关上下文、设计决策和验收标准，并允许 Claude 在工作中更新。

02

`CHANGELOG.md` 是 portable long-term memory，类似 lab notes，记录 current status、completed tasks、failed approaches、accuracy tables 和 known limitations。

03

failed approaches 必须写入进度文件，否则后续 sessions 会重新尝试同样的 dead ends；文章举例说明 stiff ODE solver 选择失败后要记录为何切换。

04

test oracle 是长期科学任务的核心。Claude 被要求用 CLASS C source 作为 reference implementation 构造并持续运行 unit tests，以防回归并衡量是否接近目标。

精读拆解 · 06

无人值守运行

01

Git 用来监控和协调无人值守进展：agent 应在每个 meaningful unit of work 后 commit and push，提交前运行指定测试，避免 compute allocation 中断导致工作丢失。

02

tmux 解决长时间终端会话的可恢复性。Agent 在 compute node 的 tmux session 中运行，研究者可以 detach、关闭电脑，再通过 SSH 重新 attach 检查或 steering。

03

SLURM 脚本负责申请 HPC 资源，例如 GPU partition、H100、48 小时 wall time，并在 job 启动后进入项目目录、激活环境、启动 Claude Code。

04

本质上，Git 提供历史与回滚，tmux 提供会话持久性，SLURM 提供计算资源边界；三者共同让 agent 的长任务执行变成可观察的实验运行。

精读拆解 · 07

Ralph Loop

01

Ralph loop 用来应对 agentic laziness：当模型声称任务完成时，loop 会把它重新拉回上下文，询问是否真的满足 specification，并促使它继续补齐缺口。

02

示例 invocation 要求 Claude 持续工作，直到 across the entire parameter range 达到 0.1% accuracy，并设置 `--max-iterations 20` 与 `DONE` completion promise。

03

作者同时提到 GSD、domain-specific variants 和 Claude Code 原生 `/loop`。这些模式的共同点是用轻量 scaffold 补足当前模型在长任务坚持性上的短板。

04

Ralph loop 不替代 oracle。它只负责推动 agent 继续执行；是否真的完成，仍必须回到精度表、测试结果、reference implementation 和人类检查。

精读拆解 · 08

结果边界

01

Claude 在多个输出上达到亚百分比一致性，但结果并非生产级。

02

文章认为，当项目有清晰成功标准时，不运行 Agent 本身也有机会成本。

结论

长任务 Agent 的可靠性来自明确判据、外置记忆和可恢复执行环境。
